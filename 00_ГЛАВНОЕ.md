## 1. Задача

Дана галерея кадров с автомобилями и набор запросов. Для каждого запроса найти в галерее тот
же автомобиль — **не используя номерной знак**. Номера в данных уже анонимизированы
пикселизацией, и финалистов дополнительно проверят на версии теста, где зона номера закрыта
сплошной заливкой.

Набор открытый (open-set): примерно у 20% запросов закрытого теста пары в галерее нет вообще,
и на них система обязана **отказаться отвечать**, а не выдать ближайшего похожего.

Детекция, трекинг, работа с видео и выбор лучшего кадра в задачу **не входят** — bbox даётся.

## 2. Что физически сдаётся

Два независимых запуска одной командой, общее ядро и общие веса.

**Конкурсный прогон** — офлайн, читает `/data`, пишет `/out` три файла:

| файл | что внутри |
|---|---|
| `embeddings.npy` | `float32 [N, D]`, строки строго: сначала все query в порядке `test_query.csv`, затем вся gallery в порядке `test_gallery.csv`. У нас D = 1536 |
| `submission.csv` | `query_id, gallery_id_1 … gallery_id_10`, **без строки заголовка**. **Ровно десять** идентификаторов на каждый запрос, всегда, даже если система отказалась |
| `candidates.csv` | заголовок строго `query_id,gallery_id,confidence`. **Отказ — это полное отсутствие строк** для данного `query_id`. Не пустые поля, не спецзначения |

```bash
docker build -t vreid:1.0 .
docker run --rm --gpus all --shm-size=2g -v /путь/к/данным:/data:ro -v /путь/куда/писать:/out vreid:1.0
```

**Прототип** — веб-интерфейс, API с OpenAPI, база: `docker compose up --build`,
открыть http://localhost:8080. Это требование ТЗ §6 и §13, а не бонус: там перечислены
микросервисное разделение, СУБД для эмбеддингов, спецификация OpenAPI, доступ через браузер
и запуск одной командой без ручных манипуляций.

## 3. Как считают баллы

| блок | вес | как считается |
|---|---:|---|
| Ранжирование | **45%** | mAP@10 по `submission.csv` |
| Производительность | **20%** | 10% латентность + 10% пропускная способность |
| Инженерное качество | 15% | Docker, воспроизводимость, код, **стек по ТЗ §6**, документация |
| Режим отказа | **10%** | `0.7 × F1 + 0.3 × TNR` |
| Защита | 10% | выступление |

Плюс §10 ТЗ — критерии арбитража при равенстве: демонстрационный веб-интерфейс,
интерпретируемость, масштабируемость на 10⁶, глубокий анализ ошибок. Закрыты все четыре.

**mAP@10.** Перед top-10 из галереи удаляются только объекты, у которых совпали **и**
`vehicle_id`, **и** `camera_id` с запросом. Другие машины с той же камеры остаются валидными
трудными негативами — удалять камеру целиком нельзя. `AP@10 = сумма(precision@rank по
релевантным позициям ≤ 10) / min(n_pos, 10)`, затем macro-усреднение. Запрос без валидных
положительных из mAP **исключается**, но в оценке отказа участвует.

**Отказ.** Исходы на уровне запроса, по строке с максимальной confidence: TP — верный топ-1
при наличии пары; FP — неверный топ-1 либо любой ответ на запрос без пары; FN — отказ при
наличии пары; TN — отказ без пары. F1 и TNR считаются **micro**. Организатор **не применяет
свой порог** к confidence: само наличие строки уже есть решение команды.

**Производительность.** Латентность `batch=1` включает чтение файла, декодирование, кроп по
bbox, препроцессинг, forward, постобработку и L2-нормализацию. Поиск по галерее и
ре-ранжирование **не входят**. Замер: медиана 300 прогонов после 50 прогревочных, CUDA sync
до и после каждого. Пропускная: устойчивый прогон не короче 10 секунд на батчах 1/8/16/32,
в балл идёт лучший FPS. Шкала: латентность ≤ 40 мс → полный балл, 40–80 линейно, > 80 → 0.
FPS ≥ 100 → полный балл, 50–100 линейно, < 50 → 0.

**Стенд жюри:** RTX A5000 24 ГБ (Ampere, sm_86), драйвер CUDA 12.2, 2× Xeon Gold 6338.

**Лимит весов 2 ГБ** — сумма ВСЕХ файлов весов. Превышение — недопуск к замеру.

## 4. Правила организаторов, которые меняют решения

Полная сводка ответов организаторов есть у команды, но в публичный репозиторий не выложена —
это их документ. Здесь только то, что продиктовало архитектуру:

* **Ответ 2.** `camera_id` есть в train и его можно использовать для сэмплирования и
  валидации, но в тесте его нет.
* **Ответ 7.** Личности train и test не пересекаются.
* **Ответ 11.** Junk-фильтр убирает только пары `vid + cam`. Это и есть метрика жюри.
* **Ответ 17.** В закрытом тесте ~20% запросов без пары; у остальных гарантирован хотя бы
  один **кросс-камерный** положительный. Про одно-камерные кадры не сказано ничего.
* **Ответ 27.** Числа 9556 / 1110 / 750 относятся к опубликованному набору и **не должны быть
  вшиты** в код: проверять надо длины фактически переданных CSV.
* **Ответ 38.** Каждый запрос независим. **Запрещены** query expansion, кластеризация по
  всему `test_query`, использование других запросов. TTA одного изображения и
  ре-ранжирование кандидатов одного запроса разрешены.
* **Ответ 39.** Сборка образа с сетью разрешена, рантайм полностью офлайн. Версии пакетов
  фиксируются точно, ссылки на подвижные теги запрещены.
* **Ответ 46.** Внешние веса и датасеты — только с однозначным URL, автором и версией.
* **Ответ 48.** Модель не должна использовать номер как признак сопоставления.
* **Ответ 49.** Строка embedding обязательна для каждого `image_id`.
* **Ответы 41/43/44.** HTTP API и UI не нужны для основной оценки, но ТЗ §6 требует их для
  инженерного блока, а §13 — ссылку на работающий прототип. Мы делаем и то и другое.

**Эталонный scorer получен 21.09** и лежит в `organizer/` с хэшами. Наша реализация
метрики сверена с ним на нашей валидации и совпадает до 1e-16 — но только после двух
исправлений, см. раздел 8. Меток закрытого теста у нас по-прежнему нет.

## 5. Что сдаём

**Релиз v1.1.** DINOv2 ViT-B/14, **вход 392**, вектор **1536** float32, L2-нормирован.
Обучение: ArcFace + батч-хард триплет, BNNeck, PK-сэмплер с кросс-камерными позитивами,
дистилляция геометрии сходств от DINOv2-L/14 336. Веса fp16, **164 МиБ**, один файл.
Скачиваются `python scripts/fetch_weights.py`, суммы сверяются.

Релиз — `release/` = усреднение весов (model soup) трёх прогонов одного рецепта
(`weights/all18_r392_s0`, `_s2`, `_s3`), 18 эпох, обучены на **всех** 1541 личности, без
отбора эпохи по валидации.

Замороженный рецепт (`release/recipe.json`):

```
confidence = top1 (сырой косинус выбранного кандидата)
threshold  = 0.55                (+ поле threshold_choice: обоснование и таблица)
kr = true, k1 = 3, k2 = 2, lam = 0.2   (k-reciprocal; выбраны по сетке, см. rerank_choice)
dba = 0, refuse_rate = null      (запрещённые ветки выключены и блокируются на входе)
crop_pad = 0.05, fast_decode = true, topk = 10
```

`predict.py` **падает на старте**, если в рецепте включены `dba`, `refuse_rate`, не-`top1`,
`topk ≠ 10` или `mask_plate` — запрещённые ветки недоступны через настройку.

Вокруг ядра — сервис: FastAPI с OpenAPI, PostgreSQL с pgvector, nginx-клиент, объяснение
решения, ANN для больших галерей. Всё поднимается `docker compose up`.

## 7. Решения и почему

**Порог отказа 0.55, а не оптимум валидации.** В нашей валидации и в открытом тесте галерея —
один кадр на трек «машина × камера», поэтому у **всех** matched-запросов есть кадр той же
машины с той же камеры, почти дубликат, медиана косинуса 0.912. Закрытый тест гарантирует
только кросс-камерную пару (ответ 17). Без дубликатов медиана падает до 0.517, и высокий
порог начинает отказывать тем, кому надо отвечать:

| порог | дубликаты есть | дубликатов нет |
|---:|---:|---:|
| 0.60 (оптимум валидации) | 96.7 | 54.4 |
| **0.55 (в релизе)** | **96.4** | **63.2** |
| 0.48 (минимакс) | 92.6 | 69.7 |

Точка безразличия — уверенность 0.913 в том, что дубликаты будут. Страховка стоит 0.08 балла
общей сотни, выплата 0.89. Решение записано в `recipe.json`, поле `threshold_choice`, чтобы
его не «починили» обратно. Воспроизведение: `python scripts/refusal_stress.py`.

**Model soup держим не ради прироста.** Прироста нет: суп из трёх прогонов одного рецепта
даёт 70.66 при среднем участников 70.54 (+0.12). Но **разброс между сидами одного рецепта —
2.9 пункта** (`fit18_s0` 71.63, `fit18_s2` 71.24, `fit18_s3` 68.73). Выбирать «лучший
одиночный» по валидации на таком шуме — лотерея. Суп даёт то же матожидание при меньшей
дисперсии и не стоит ни миллисекунды на инференсе. Так его и надо защищать.

**k-reciprocal 3/2/0.2, без DBA.** DBA и query expansion запрещены ответом 38; строка с DBA
выглядит лучше (75.0), использовать её нельзя. Ре-ранжирование не входит в замер латентности,
поэтому оно бесплатно по баллам — и поэтому же его параметры надо искать всерьёз. Прежние
6/2/0.3 были первой строкой грубой сетки, то есть краем диапазона; полная сетка из 93 точек
дала оптимум внутри, 3/2/0.2, и он совпал на двух независимых кешах (ранговая корреляция
поверхностей 0.957). Прирост mAP +0.57 и +1.09 п.п., rank-1 +1.13 и +1.03, режим отказа не
меняется вовсе — ре-ранжирование не сдвигает топ-1 ни у одного из 1213 запросов. Разрыв до
запрещённого DBA сократился с 1.2 до 0.7 п.п. Подробности — `release/recipe.json`, поле
`rerank_choice`; воспроизвести — `python scripts/rerank_grid.py`.

**Уверенность оставлена сырым косинусом.** Проверены четыре меры (`top1`, `margin`,
`gap_to_rest`, `ratio`) на том же стрессе, что и порог, каждая со своим лучшим порогом по
ожиданию. Разброс ожиданий 82.4–87.1 при 86.6 у `top1`; лучшая, `gap_to_rest`, выигрывает
0.5 балла отказа, то есть 0.05 общей сотни. Это внутри шума прогонов и не стоит изменения
замороженного пути принятия решения. Числа — `results/confidence_stress.json`.

**Ансамбль и TTA отвергнуты.** Ансамбль из двух моделей удваивает время сети. При линейной
шкале mAP потеря пропускной способности окупается только приростом порядка +5.3 п.п. mAP,
которого TTA-флип не даёт (обычно 0.3–1.0).

**Вход 392 вместо 336 — главный прирост v1.1, и он безрисковый.** Шкала производительности
опубликована, и на 336 мы тратили её не целиком (28.5 мс из 40, 195.7 FPS при пороге 100).
Кропы крупные — медиана короткой стороны 846 px, — так что на 336 модель видела вчетверо меньше
пикселей, чем есть в кадре. Разведка по одному сиду: 392 → 76.84, 448 → 78.17 при трёх сидах
336 в диапазоне 71.8–75.4. Выбор между 392 и 448 сделан по замеру настоящего конвейера: у 448
запас по пропускной 11%, у 392 — 52%, а перевес 448 лежит внутри разброса сидов. Суп на 392:
**74.21 → 77.41**. `results/resolution_choice.json`.

**Каскад с ViT-L — реализован, измерен и выключен.** Ре-ранкер DINOv2-L/14 уточняет порядок
внутри топ-30 и даёт поверх v1.1 ещё +2.80 (77.41 → 80.21; поверх 336 давал +4.77). Правила
ре-ранжирование из замера латентности исключают (ответы 31, 32) и вес ре-ранкера считают в
общий лимит (ответы 34, 37). Но настоящая цена запроса с ним — 46 мс и 62 FPS, и если жюри
засчитает второй форвард, производительность падает с 20 до 10.9. Минус девять против плюс
одного с третью: выбран путь, чей балл не зависит от трактовки. Включается одним полем рецепта,
ре-ранкер лежит в релизе v1.0. Разбор — `vreid/cascade.py`, `results/cascade_verify_r392.json`.

**Номер.** В бою ничего не закрашивается: детектор зоны номера стоит 50 мс на кроп при
бюджете 8 и нужен только для абляции. Абляция с контролем равной площади: закрыть зону номера
−0.35, закрыть столько же пикселей в другом месте −0.33, то есть **опора на номер 0.02 п.п.**
при разбросе прогонов 0.2–0.3. То же видно глазами: в интерфейсе кнопка «Почему похоже»
показывает точное разложение косинуса по участкам кадра, и зона номера не подсвечена.

**Независимость запросов** обеспечена по построению: столбцы запросов исключены из соседства
в k-reciprocal, матрицы считаются фиксированной формы, сортировки стабильные, память
ограничивает размер пачки, а не выбор алгоритма. Проверки:
`scripts/check_tie_independence.py`, `scripts/check_query_independence.py`.

**Галерея сервиса привязана к отпечатку извлечения, а не к хэшу рецепта.** Вектор зависит от
весов и от `crop_pad` / `fast_decode` / `tta_flip`. Порог отказа на вектор не влияет, и
привязка к хэшу всего файла означала бы пересчёт миллиона эмбеддингов из-за правки одного
числа. Смена весов или параметров кропа отпечаток меняет, и хранилище честно отвергается.

## 8. Что отозвано

**«−7.3 пункта только от размера галереи» — отозвано.** Тот эксперимент менял размер галереи
и состав запросов одновременно, поэтому мерил не то. Правильная схема — запросы и все их
положительные зафиксированы, добавляются только отвлекающие — поставлена
(`results/gallery_size_effect_fixed.json`), но упирается в данные: из 688 строк галереи лишь
**5** не являются положительными ни для одного запроса. Измеримый диапазон 683→688 даёт
**0.01 п.п.** Экстраполировать это на разницу 688 против 750 нельзя: пять точек ничего не
говорят о форме зависимости. Качественное возражение остаётся, количественного обоснования
нет, и приводить его на защите нельзя.

**«Нативный прогон совпадает с контейнерным» — отозвано.** Очередь 14 впервые сравнила их
напрямую: расходятся 35 ячеек ранжирования из 11 100 (0.3%), эмбеддинги до 4.5e-04. Причина —
разные версии Pillow и NumPy. В зачёт идёт контейнер, и внутри одного образа всё
детерминировано бит в бит.

**Числа 72.0 / 74.9 — устарели**, см. раздел 6. Они со старого `soup_b336_val`, который
собран иначе (смешанные рецепты, отбор эпохи по валидации, 20 эпох) и релиз не представляет.

**`release_soup_fast/` — не релиз-кандидат.** Автовыбор уверенности подсунул там `top1+bits`,
а `bits` прямо зависит от размера галереи, который на тесте 750, а на валидации 688.

## 9. Что открыто

1. **Официальный `evaluate.py` и `example_submission.zip`** — не получены.
2. **Прогон на A5000** — не делался. Замеры сняты на RTX 5060 Ti в CUDA 12.8.
3. **Порог откалиброван на галерее 688, на тесте 750.** Направление влияния известно,
   величина — нет (см. раздел 8).
4. **Релизный образ проверен на CPU, не на Ampere.** Он собирается, проходит `pip check`,
   отрабатывает конкурсный прогон целиком (669 с на CPU) и пишет корректные файлы. Но
   запустить его на CUDA-карте этой машины нельзя: у неё sm_120, которого нет в CUDA 12.1.
   Все GPU-замеры сняты на dev-образе.

Закрыто с прошлой редакции: релизный образ пересобран и собирается (была главная дыра),
замер приписан релизу, продукт из ТЗ §6 собран и проверен целиком.
