# Архитектура решения

Документ описывает, из каких компонентов состоит система, кто за что отвечает и почему
границы проведены именно так. Метрики и обоснование порога — в корневом `README.md`,
разбор ошибок — в `ERROR_ANALYSIS.md`.

## 1. Что решает система

Дана галерея кадров с автомобилями и запрос: кадр плюс рамка автомобиля. Нужно найти в
галерее тот же автомобиль, **не используя номерной знак**, и — отдельно — уметь
**отказаться отвечать**, если подходящего автомобиля в галерее нет.

Задача открытая (open-set): примерно у пятой части запросов пары в галерее нет вовсе.
Личности в обучении и в тесте не пересекаются, так что запоминание конкретных машин
не работает в принципе — нужен признак, переносимый на невиданные автомобили.

## 2. Компоненты

```
                    ┌──────────────────────────────────────────────┐
  браузер  ───────▶ │  web   nginx: страница, статика, единственный │
  :8080             │        публикуемый порт, обратный прокси      │
                    └───────────────┬──────────────────────────────┘
                                    │ /v1, /health, /docs, /openapi.json
                    ┌───────────────▼──────────────────────────────┐
                    │  api   FastAPI + ядро vreid + веса релиза     │
                    │        кроп → эмбеддинг → поиск → отказ       │
                    │        объяснение, ANN-шортлист, OpenAPI      │
                    └───────┬──────────────────────┬───────────────┘
                            │ SQL                  │ файлы модели
                    ┌───────▼───────────┐   ┌──────▼──────────────┐
                    │  db  PostgreSQL   │   │ release/            │
                    │      + pgvector   │   │  model.pt           │
                    │  кадры, рамки,    │   │  recipe.json        │
                    │  векторы 1536D    │   │  (замороженный)     │
                    └───────────────────┘   └─────────────────────┘

  отдельно, той же кодовой базой и теми же весами:
                    ┌──────────────────────────────────────────────┐
  /data ──────────▶ │  predict  конкурсный batch-инференс           │ ──▶ /out
                    │  embeddings.npy, submission.csv,              │
                    │  candidates.csv                               │
                    └──────────────────────────────────────────────┘
```

Три работающих компонента и один пакетный запуск. Разделение не декоративное:

* **web** не знает ни про модель, ни про базу. Он отдаёт статическую страницу и проксирует
  всё остальное. Заменить его на любой другой фронт можно, не трогая остальное.
* **api** не хранит состояние. Галерея живёт в базе, веса — в образе, а сам процесс можно
  перезапустить в любой момент: проверено, галерея переживает перезапуск.
* **db** не знает про модель. Она хранит кадр, рамку и уже нормированный вектор, плюс
  отпечаток модели и рецепта. Галерея, собранная другой моделью, не будет молча
  переиспользована — это ошибка, а не предупреждение.
* **predict** не зависит ни от чего из перечисленного. Конкурсный прогон — это одна команда,
  читающая `/data` и пишущая `/out`, без базы, без сети и без HTTP.

Почему batch-инференс не сделан вызовом сервиса: у него другой контракт корректности.
Жюри запускает его одной командой в изолированном окружении, и никакая часть продукта не
должна иметь возможности изменить его результат. Общие у них только ядро `vreid/` и
`release/` — то есть ровно то, что и должно быть общим.

## 3. Путь одного запроса

1. **Приём.** `POST /v1/search`: кадр (JPEG/PNG/WebP), рамка `x,y,w,h` в пикселях исходного
   кадра, необязательный `query_id`. Проверяются формат, размер, число пикселей и то, что
   рамка лежит внутри кадра.
2. **Кроп.** `vreid.extract.open_crop` — тот же код, что в конкурсном прогоне: паддинг
   `crop_pad` из рецепта, ускоренный декод JPEG в уменьшенном масштабе, когда рамка это
   позволяет.
3. **Эмбеддинг.** DINOv2 ViT-B/14, вход 336, `concat(CLS, mean(patch))` → BNNeck →
   L2-нормализация. Вектор 1536 float32. Операции модели сериализованы: одна за раз,
   конкурирующий запрос получает 503 с `Retry-After`, а не тихую очередь.
4. **Поиск.** Косинус против всей галереи. Кадры того же исходного файла исключаются.
   В режиме `ann` перед этим строится шортлист HNSW — меняется только состав кандидатов,
   сам косинус считается так же.
5. **Ре-ранжирование.** k-reciprocal 3/2 с λ=0.2 внутри одного запроса и галереи. Другие запросы
   не участвуют ни на одном шаге — это требование правил, а не оптимизация.
   В конкурсном прогоне за ним идёт вторая ступень каскада: порядок внутри топ-30 уточняет
   ViT-L/14 (`release/reranker.pt`, `vreid/cascade.py`). Демонстрационный API её пока не
   выполняет — он ранжирует по векторам, которые хранит база, а вектора тяжёлой модели в
   схеме нет. Это расхождение демо и сдачи названо здесь намеренно: балл за точность
   считается по `submission.csv`, который делает `vreid/predict.py`, и там каскад есть.
6. **Решение.** Уверенность — сырой косинус выбранного кандидата. Выше порога из рецепта —
   кандидат принят; ниже — отказ: `accepted=false`, `candidate=null`. Ранжирование
   возвращается в обоих случаях: оператору оно полезно, но в конкурсный `candidates.csv`
   отказной запрос не попал бы ни одной строкой.
7. **Объяснение** (по запросу). `POST /v1/explain` раскладывает косинус пары по участкам
   обоих кадров точно, без градиентов — см. раздел 5.

## 4. Данные и их границы

| что | где лежит | кто пишет |
|---|---|---|
| кадр, рамка, вектор, отпечаток модели | таблицы `gallery_items`, `gallery_metadata` | api |
| веса и рецепт | `release/` внутри образа | сборка |
| результаты замеров | `results/*.json` | скрипты проверок |
| артефакты сдачи | `submission/` | конкурсный прогон |

Вектор кладётся в базу уже нормированным и больше не меняется. Нормализовать его в
хранилище было бы тихой подменой числа, по которому потом считается порог отказа.

Тип колонки — `vector(1536)` расширения pgvector, а не набор байт: база умеет считать
расстояния сама, и для городских объёмов над ней можно построить индекс, не меняя схему.
Сходство при этом считает ядро — чтобы ответ HTTP совпадал с конкурсным CLI точно, а не
приблизительно. Это совпадение проверяется тестом на реальной сдаче
(`tests/service/test_core.py`).

## 5. Интерпретируемость

Обычный ответ на вопрос «куда смотрела модель» — Grad-CAM. Здесь он не нужен: у нашей
архитектуры вклад каждого участка в косинус выписывается **точно**.

Эмбеддинг собирается как `f = concat(CLS, mean_p token_p)`, дальше BNNeck — поэлементная
аффинная функция в режиме вывода, дальше нормализация. Усреднение по патчам линейно,
поэтому косинус раскладывается в сумму вкладов патчей плюс постоянная часть:

```
cos(z_q, z_g) = Σ_p w(p) + const
w(p) = (1/‖b_q‖)·(1/P)·Σ_j a_[C+j]·token_p,j·z_g,[C+j]
```

`w(p)` измеряется в тех же единицах, что и сам косинус. Сумма частей равна целому — ответ
API содержит `reconstruction_error`, и на релизной модели он равен нулю. Карта считается
симметрично для запроса и для кандидата: «куда смотрел запрос» и «чем ответил кандидат» —
разные вопросы.

Побочный, но важный эффект: на картинке видно, что зона номера не подсвечена. Это то же
утверждение, что и абляция с контролем равной площади, но его можно показать мышкой.

## 6. Масштабируемость

Поиск по галерее не входит в замер производительности жюри — туда входят чтение,
декодирование, кроп, препроцессинг, forward и нормализация. Поэтому масштабируемость здесь
не про балл, а про то, что будет при городских объёмах.

`scripts/ann_benchmark.py` меряет три режима на галереях 10⁴, 10⁵ и 10⁶ векторов
размерности релиза. Вектора синтезируются по ковариации настоящих эмбеддингов: у белого
шума нет структуры, на которой работает PCA, и любой ANN на нём выглядел бы плохо по
причине, не имеющей отношения к делу. У каждого запроса есть подсаженный правильный ответ,
поэтому меряется не только совпадение списков, но и доля найденных правильных ответов.

Тот же индекс встроен в боевой путь и включается параметром `mode=ann`, чтобы разницу
можно было увидеть, а не принять на слово. Ниже 256 записей ANN не включается: обход графа
дороже полного перебора, и сервис честно об этом пишет в ответе.

## 7. Границы текущей версии

* Один процесс, одна операция модели одновременно, до 1500 наблюдений в галерее.
  Горизонтальное масштабирование потребовало бы вынести индекс из процесса — схема это
  допускает (вектор уже в СУБД), но в этой версии не сделано.
* Импорт ZIP синхронный: на CPU большой архив обрабатывается минуты.
* Ролей пользователей нет. Есть общий ключ доступа `X-API-Key`, который включается
  переменной окружения; по умолчанию наружу публикуется только веб-слой.
* Детекция, трекинг и выбор лучшего кадра в задачу не входят: рамка даётся на входе.
