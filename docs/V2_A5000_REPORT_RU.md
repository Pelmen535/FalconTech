# v2.0: итоговая проверка Linux / RTX A5000, 20 октября 2026

Выбрана и проверена **October A**, без изменения весов, математики ранжирования, heads и порогов отказа. Экспериментальные rho-gate и новые ранжировщики не приняты. v2.0 объединяет текущую модель и инженерный функционал сервиса: HTTP/CLI, PostgreSQL/SQLite, явные feature_ref, миграция, резервные копии, восстановление worker и контролируемые deadlines.

## 1. Зафиксированная сборка и среда

- Ubuntu 22.04.5; RTX A5000 24 ГиБ; driver 570.211.01.
- Docker: Python 3.12, PyTorch 2.11 / CUDA 12.8, TensorRT 10.9.0.34. Полный пакетный lock: `requirements-robust-linux.lock`; источники и лицензии: [SOURCES](../SOURCES.md).
- Runtime manifest SHA-256: `0e24cd2cc802518cba3cf094c40411fa933efa6701a168231d396bd066545a35`.
- Проверенный локальный image ID: `sha256:fa4ad6c08349f6b2b66eeb122f65f3047685b4d569ac5995f494fe32c28b323a`.
- Активные веса: **1 838 245 659 байт**, меньше 2 000 000 000; ONNX-дубликаты не включены. Все 16 файлов проверяются по размеру и SHA-256.
- Полный Dockerfile окружения собран из закреплённого публичного PyTorch base, с pip check и проверкой весов. Итоговый образ дополнен небольшим слоем квалификационных metadata/compose; закреплённые inference-исходники и веса не изменились. Затем итоговый образ проверен без подмены `/app` через bind mount.

Точное воспроизведение CUDA 12.2 организаторского стенда не подтверждено. Image ID идентифицирует проверенную локальную сборку; новая сборка из Dockerfile не обязана иметь тот же image ID из-за метаданных слоёв.

## 3. Производительность

Согласованное сравнение: одни и те же 64 JPEG и bbox, 8 CPU / 16 ГиБ RAM, 4 preprocessing workers, torch threads 2; 50 прогревов, 300 B1 с CUDA synchronization, по 30 секунд B1/8/16/32; по два завершённых процесса. Порядок v1.4-A / October-before-A / v2-A / v2-B / October-before-B / v1.4-B.

| Версия | B1 median, мс | B1 p95, мс | лучший batch FPS | выборочный максимум GPU, МиБ |
|---|---:|---:|---:|---:|
| v1.4 release | 29.07–29.23 | 31.96–33.07 | 131.44–139.34 | 1625 |
| October A до оптимизации | 36.74–36.95 | 61.03–61.67 | 128.54–128.67 | 3745 |
| v2.0 | 35.41–35.74 | 40.90–40.92 | 132.50–134.58 | 1497 |

Это as-deployed PyTorch v1.4 против TensorRT v2.0, а не одинаковая численная точность. v2.0 сокращает память относительно прежней October A примерно на 60%, но не обгоняет v1.4 по B1 latency. Два прогона не дают основания обещать статистически значимое преимущество при любой нагрузке.

Дополнительный прогон **окончательного образа**: 50 прогревов, 300 B1, по 10 секунд на batch:

- B1 median **34.5807 мс**, p95 **39.2848 мс**.
- FPS batch 1/8/16/32: **49.74 / 122.57 / 132.19 / 135.72**.
- Выборочный максимум GPU **1497 МиБ**, process RSS **2 033 065 984 байт**.
- Повтор одного входа maxabs 0; batch1/8 vs16 maxabs < 1e-7.

Оба протокола включают JPEG, decode, crop, preprocessing, encoders и feature transforms/L2; подготовка статической галереи, поиск, отказ и HTTP не входят. Prefetch допускает перекрытие CPU/GPU. Это не 135 HTTP-запросов/с. `nvidia-smi` каждые 250 мс даёт выборочный максимум выделенного GPU, не точный allocator peak и не универсальный предел памяти.

Реальный HTTP на 688 gallery: регистрация 28.19 с; первый query 1381 мс с подготовкой gallery, следующие в последовательности 69–105 мс. Это отдельный сервисный сценарий, не benchmark извлечения.

Исправлены две реальные инженерные ошибки: native TensorRT stdout мог портить JSON-RPC (Linux control FD изолирован); internal-only Docker network не публиковала nginx port (web получил отдельный frontend bridge, API/DB остались internal). При последнем replay исправлена подготовка QA-каталога: добавлен отсутствовавший bind-mounted nginx.conf. Математика модели не менялась.

Провалы первых попыток сохранены локально. Ошибка transport закрытия SSH после завершённого CPU/длинного worker не считается падением inference: отдельно считаны exit0 и итоговый proof. Дисковый guard 5 ГиБ не снижался; освобождались только проверенные собственные копии весов и собственный BuildKit context cache, старые модели и данные сохранены.

## 5. Известные ограничения и воспроизведение

- VRIC: текущий reranking имеет подтверждённую регрессию retrieval относительно fused cosine; принятый вариант сохраняется, так как новые кандидаты не прошли все исходные критерии. Не заявляется исправление этой проблемы.
- Recall на VRIC остаётся низким; для новых доменов устойчивость не доказана.
- Нет закрытого теста, нового независимого holdout и официальной проверки дополнительной заливкой номера.
- Нет точного CUDA12.2 replay, миллионной галереи и доказанного выигрыша ANN по скорости.
- Выборочные GPU samples не доказывают абсолютный пик при любой галерее. Лимит 2 млрд байт относится к весам; его нельзя подменять утверждением о 2 ГиБ VRAM.
- Синтетические/unit-проверки не заменяют указанные реальные Linux-прогоны; саморевью не является независимой экспертизой.
