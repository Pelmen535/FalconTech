# Сервис безномерной идентификации транспортного средства

Команда **«Связанные одной цепью»**: ядро и обучение — Шека Николай, сервис и интеграция —
Исмаков Марат.

Система находит один и тот же автомобиль на кадрах с разных камер **без использования
государственного номера** и умеет **отказаться от ответа**, когда подходящего автомобиля в
базе нет. Решение опирается только на внешний вид кузова: на кадрах номер закрыт, а отдельная
проверка показала, что модель на эту зону не опирается.

| | |
|---|---|
| модель | DINOv2 ViT-B/14, вход 392×392, вектор 1536, один файл весов 164 МиБ |
| точность на машинах, которых модель не видела | mAP@10 **82.70**, rank-1 **80.41** |
| режим отказа, 0.7·F1 + 0.3·TNR | **96.68** при пороге 0.67 |
| скорость извлечения признака | **35 мс** на автомобиль (batch = 1), **132 кадра/с** в пакетном режиме |
| воспроизводимость | два прогона подряд совпадают бит в бит |

Два способа запуска, оба одной командой и на одних весах: **веб-сервис** (интерфейс, API,
база) и **пакетный прогон** (папка с кадрами и CSV → три выходных файла).

## 1. Быстрый старт

### 1.1 Веса

Веса не хранятся в git, они опубликованы файлами GitHub-релиза. Скрипт скачивает их в
`release/` и сверяет SHA-256 с `release/weights.json`; зависимостей у него нет, только
стандартная библиотека.

```bash
python scripts/fetch_weights.py
```

### 1.2 Веб-сервис

```bash
cp .env.example .env          # при необходимости поправьте порт и устройство
docker compose up --build
```

Поднимаются три контейнера: `db` (PostgreSQL + pgvector), `api` (инференс и HTTP), `web`
(nginx, тонкий клиент). Наружу публикуется только `web`:

| адрес | что это |
|---|---|
| http://localhost:8080 | веб-интерфейс |
| `/docs` | Swagger UI — интерактивная документация API, работает без интернета |
| `/openapi.json` | спецификация OpenAPI |
| `/health` | состояние сервиса, хранилище, отпечатки модели и рецепта |

Работа в интерфейсе:

1. **Галерея** → «Импорт галереи из ZIP» → «Импортировать». Архив: `test_gallery.csv`
   (`image_id,x,y,w,h`) и папка `images/`. Можно добавлять и по одному кадру, выделяя
   автомобиль мышью.
2. **Поиск** → загрузить кадр → выделить автомобиль мышью → «Найти автомобиль». Результат —
   «Совпадение найдено» или «Совпадение не найдено», десять ближайших наблюдений с
   уверенностью и выгрузка в CSV или JSON.
3. **Почему похоже** под любым кандидатом — карта сходства на обоих кадрах: какие участки
   кузова совпали сильнее всего.
4. **О системе** — параметры модели, порог и замеры поиска на галереях до миллиона
   наблюдений.

Архив на 20 кадров для быстрого знакомства собирается из выданного набора данных:

```bash
python scripts/make_demo_gallery.py --data <папка с images/ и test_*.csv>   # -> demo/gallery.zip
```

### 1.3 Пакетный прогон

```bash
docker build -t vreid:1.0 .
docker run --rm --gpus all --shm-size=2g \
  -v /путь/к/данным:/data:ro -v /путь/куда/писать:/out vreid:1.0
```

или через compose: `docker compose run --rm predict`.

Читает `/data/images`, `/data/test_query.csv`, `/data/test_gallery.csv`, пишет в `/out`:

| файл | содержимое |
|---|---|
| `embeddings.npy` | `float32 [N, 1536]`: сначала все запросы в порядке `test_query.csv`, затем вся галерея в порядке `test_gallery.csv` |
| `submission.csv` | `query_id, gallery_id_1 … gallery_id_10` без строки заголовка, ровно десять кандидатов на каждый запрос |
| `candidates.csv` | заголовок `query_id,gallery_id,confidence`; отказ — это отсутствие строк для данного `query_id` |
| `run_info.json` | время, число отказов, отпечатки модели, рецепта и входных CSV |

Прогон полностью офлайн (`HF_HUB_OFFLINE=1`, веса внутри образа; проверено запуском с
`--network none`). `--shm-size=2g` нужен загрузчику данных: без него прогон не падает, а сам
снижает число воркеров.

### 1.4 Если что-то не собирается

* **Видеокарта RTX 50xx (Blackwell, sm_120).** Основной образ собран на CUDA 12.1 под RTX
  A5000 и на Blackwell не запускается. Для такой карты — сборка на CUDA 12.8: раскомментируйте
  три строки в конце `.env.example`, либо
  ```bash
  docker build --build-arg BASE_IMAGE=pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime \
               --build-arg PIP_FLAGS=--break-system-packages \
               --build-arg REQUIREMENTS=requirements-infer-dev.txt -t vreid-dev .
  ```
* **Нет GPU.** Основной compose резервирует видеокарту. Для машины без NVIDIA-рантайма:
  ```bash
  docker compose -f docker-compose.yml -f docker-compose.cpu.yml up --build
  ```
  Модель и ответы те же, отличается скорость: импорт двадцати кадров и поиск занимают около
  12 секунд вместо долей секунды. Пакетный прогон на CPU — тот же `docker run` без `--gpus all`.
* **Путь с кириллицей.** buildkit не собирает через `bake`, если путь к проекту не ASCII.
  Помогает `COMPOSE_DOCKER_CLI_BUILD=0 docker compose build` или каталог с латинским именем.

## 2. Архитектура

Подробно — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), API — [`docs/API.md`](docs/API.md).

```
браузер ──▶ web (nginx: страница и единственный публикуемый порт)
                 │ /v1, /health, /docs, /openapi.json
                 ▼
            api (FastAPI + ядро vreid + веса релиза)
                 │ SQL                      │ файлы модели
                 ▼                          ▼
            db (PostgreSQL + pgvector)   release/model.pt + recipe.json

то же ядро и те же веса, отдельным запуском:
  /data ──▶ predict (пакетный, офлайн) ──▶ embeddings.npy, submission.csv, candidates.csv
```

Пакетный прогон не зависит от сервиса: у него свой контракт — одна команда в изолированном
окружении, и никакая часть сервиса не может повлиять на его результат. Общее у них — ядро
`vreid/` и каталог `release/`. Ответ сервиса совпадает с пакетным прогоном: те же десять
кандидатов, те же решения об отказе, тот же косинус до пятого знака
(`tests/service/test_core.py`; тесту нужен локальный прогон на реальных данных, без них он
пропускается).

## 3. Модель

**Backbone.** DINOv2 ViT-B/14, вход 392×392, эмбеддинг `concat(CLS, mean(patch tokens))` через
BNNeck → 1536 float32, L2-нормирован. Веса fp16, 164 МиБ.

**Обучение.** ArcFace + batch-hard триплет, BNNeck, PK-сэмплер с кадрами одной машины с
разных камер. Дистилляция геометрии сходств (Tung & Mori): ученик перенимает у учителей не
векторы, а матрицу попарных косинусов внутри батча. Учителей два — DINOv2-L/14 на входе 336
(первые 8 блоков заморожены) и предыдущая версия модели (v1.3); цель — среднее их матриц
сходств. Трудные пары — та же машина с другой камеры и четыре ближайшие по учителю чужие
машины — весят в лоссе дистилляции в пять раз больше остальных. 18 эпох на всех 1541 машинах
обучающей выборки, без отбора эпохи по валидации.

**Усреднение весов (model soup).** Релиз — среднее весов трёх обучений одного рецепта с
разными сидами. Разброс между отдельными сидами на ранних рецептах доходил до 2.9 пункта
mAP; суп даёт то же ожидание при меньшей дисперсии и ничего не стоит на инференсе.

**Инференс.** Кроп по рамке с паддингом 5%, ускоренный декод JPEG в уменьшенном масштабе
(когда рамка это позволяет), forward, L2-нормализация. Ранжирование — косинус, затем
k-reciprocal (`k1=3, k2=2, λ=0.2`) внутри одного запроса. Решение по запросу не зависит от
других запросов: их столбцы исключены из соседства, матрицы фиксированной формы, сортировки
стабильные (`scripts/check_query_independence.py`: при удалении и перестановке остальных
запросов топ-10 совпал у 666 из 666; `scripts/check_tie_independence.py`: расхождение 0 на
точных ничьих и при любом размере пачки).

### 3.1 Как модель улучшалась

mAP@10 на отложенной валидации:

| версия | что изменилось | mAP@10 |
|---|---|---:|
| v1.0 | ViT-B/14 на входе 336, дистилляция от ViT-L (вес 20) | 74.21 |
| v1.1 | вход 392 вместо 336 | 77.41 |
| v1.2 | вес дистилляции 40 | 78.42 |
| v1.3 | фокус дистилляции на трудных парах | 81.82 |
| **v1.4** | второй учитель — сама v1.3 | **82.70** |

* **Вход 392.** Медиана короткой стороны кропа — 846 px: на входе 336 модель видела вчетверо
  меньше пикселей, чем есть в кадре. Уже обученная модель на большем входе прироста не даёт,
  нужно переобучение. 448 оказался точнее на одном сиде, но в пределах разброса сидов и с
  запасом по пропускной всего 11%; выбран 392 (`results/resolution_choice.json`,
  `results/resolution_budget.json`).
* **Вес дистилляции 40.** Парно против тех же сидов на весе 20: 73.33 → 75.17 и 73.21 → 75.40
  без постобработки при разбросе сидов 0.30 (`results/training_dw40_r392.json`).
* **Фокус на трудных парах.** Раньше лосс дистилляции усреднял ошибку по всем парам батча
  поровну, хотя трудных пар в нём около пятой части. С фокусом: 75.17 → 79.21 на одном сиде,
  75.23 → 79.46 на супе без постобработки. Ученик ViT-B впервые обогнал учителя ViT-L (78.32)
  (`results/gate_probe_focus4.json`, `results/gate_students_f4.json`).
* **Второй учитель.** v1.3 сильнее ViT-L и ошибается иначе; среднее двух матриц сходств дало
  ещё +0.88 на супе (`results/gate_students_f4t2.json`).

Инференс при всех этих шагах, кроме смены входа, не менялся — меняется только обучение.

### 3.2 Каскад со второй моделью

Реализован уточняющий проход (`vreid/cascade.py`): порядок внутри топ-30 пересчитывает
DINOv2 ViT-L/14. Поверх v1.4 он добавляет +0.86 mAP@10 (82.70 → 83.56 при весе смешивания
0.5), но добавляет к каждому запросу проход тяжёлой модели: в замере на v1.0 латентность росла
с 28.5 до 46 мс, пропускная падала со 196 до 62 кадров/с.
В релизе выключен (`"cascade": false` в рецепте). Включается полями `"cascade": true` и
`"cascade_alpha": 0.5` в `release/recipe.json` и файлом `reranker.pt` из GitHub-релиза v1.0
(`results/cascade_verify_r392dw40f4t2.json`).

## 4. Качество и скорость

### 4.1 Как считается точность

Метрика — mAP@10: из галереи исключаются только наблюдения, у которых совпали **и**
`vehicle_id`, **и** `camera_id` с запросом; AP@10 нормируется на `min(n_pos, 10)`; запрос без
пары исключается из mAP, но участвует в оценке отказа. Числа посчитаны официальным скриптом
метрики (`evaluate.py`, в репозиторий не входит), наша реализация совпадает с ним до 1e-16.

Модель для замеров — «двойник» релиза: тот же рецепт, те же сиды и эпохи, но обучен без 307
машин отложенной валидации (1213 запросов, галерея 688, 243 запроса без пары). Сам релиз
обучен на всех машинах, и измерить его на отложенной части нельзя.

| | v1.4 | источник |
|---|---:|---|
| mAP@10 без постобработки | 79.88 | `results/hack_ft_soup_r392dw40f4t2_fit_val.json` |
| **mAP@10 (как в релизе, с k-reciprocal)** | **82.70** | `results/official_validation/official_report.json` |
| rank-1 | 80.41 | там же |
| rank-5 | 91.65 | там же |
| mAP по полному ранжированию | 80.45 | там же |
| **отказ: 0.7·F1 + 0.3·TNR** при пороге 0.67 | **96.68** (F1 96.67, TNR 96.71) | там же |
| отказ без кадров той же камеры в галерее | 66.22 | `results/refusal_stress_r392dw40f4t2.json` |
| отказ на половине машин, не участвовавшей в выборе порога | 96.75 | `results/refusal_audit_r392dw40f4t2.json` |

### 4.2 Скорость

Латентность — медиана 300 прогонов batch = 1 после 50 прогревочных, с синхронизацией CUDA; в
неё входят чтение, декодирование, кроп, препроцессинг, forward и нормализация, поиск по
галерее — нет. Пропускная — устойчивый прогон не короче 10 секунд на пачках 1/8/16/32, лучший
результат. Целевые значения: не больше 40 мс и не меньше 100 кадров в секунду.

| | v1.4 |
|---|---:|
| латентность batch = 1, медиана | **35.1 мс** (повторные прогоны 32.8–35.2) |
| из неё чтение, декодирование, кроп и препроцессинг | 22.6 мс |
| пропускная (batch 8) | **132.2 кадра/с** (повторные прогоны 137–140) |
| размер весов | 164 МиБ |
| пик видеопамяти | 1801 МиБ |
| загрузка весов | 3.0 с |
| прогон на открытом тесте, 1860 кропов | 89.1 с |

Замер снят на RTX 5060 Ti в окружении CUDA 12.8 (`results/bench_full.json`; файл хранит
отпечатки модели и рецепта). Запас до целевых значений — 12% по латентности и 32% по
пропускной.

### 4.3 Воспроизводимость

| что сравнивалось | результат |
|---|---|
| два одинаковых запуска контейнера | совпали бит в бит (0 из 11 100 ячеек) |
| запуск с `--network none` | совпал бит в бит — прогон действительно офлайн |
| запуск без `--shm-size` | совпал бит в бит |
| нативный прогон против контейнерного | 35 ячеек ранжирования из 11 100 (0.3%): разные версии Pillow и NumPy по-разному округляют на точных ничьих |
| образ на CPU против образа на GPU | 88 ячеек из 11 100 (0.8%), топ-1 разошёлся у 1 запроса из 1110, число отказов то же |

Внутри одного образа результат детерминирован при любом числе воркеров и размере пачки.

## 5. Порог отказа

Отказ означает, что уверенность лучшего кандидата — его косинус — ниже порога **0.67**. Порог
записан в `release/recipe.json` вместе с обоснованием (поле `threshold_choice`) и во время
работы не меняется.

Порог выбирается правилом, а не вручную (`scripts/choose_threshold.py`). На валидации у
запроса с парой в галерее почти всегда есть кадр той же машины с той же камеры — почти
дубликат с очень высокой уверенностью. В реальном применении такого кадра может не быть:
гарантирована лишь пара с другой камеры, и уверенность там заметно ниже. Слишком строгий порог
начал бы отказывать как раз там, где совпадение есть. Правило — максимум ожидаемого качества
отказа при вероятности 0.85, что такой дубликат в галерее будет. Эта вероятность опирается на
измерение: на открытом тесте уверенность лучшего ответа распределена так же, как на валидации с
дубликатами (у 77% запросов не ниже 0.8; на валидации с дубликатами — у 64%, без них — у 1.6%).

| порог | галерея с дубликатами | галерея без дубликатов |
|---:|---:|---:|
| 0.70 (оптимум валидации) | 97.1 | 59.7 |
| **0.67 (в релизе)** | **96.7** | **66.2** |
| 0.55 (минимакс по двум сценариям) | 89.7 | 76.3 |

На открытом тесте порог даёт 86 отказов из 1110 (7.7%). Воспроизвести:
`python scripts/refusal_stress.py`, затем
`python scripts/choose_threshold.py --stress <отчёт> --out <файл>`.

## 6. Номерной знак

Номера на кадрах закрыты пикселизацией: на номер шириной 320 px приходится 4–5 ячеек, от
символов не остаётся ничего. Остаются положение, размер и средний цвет пятна, поэтому проведена
абляция с контролем равной площади: зона номера находится детектором (`vreid/plate.py`, на 94.0%
из 11 416 кропов) и закрывается заливкой; контроль — такой же по площади прямоугольник там, где
номера нет.

| вариант | mAP@10 | Δ |
|---|---:|---:|
| без маски | 72.0 | — |
| зона номера закрыта | 71.6 | −0.35 |
| контроль: та же площадь выше по кузову | 71.6 | −0.33 |
| контроль: та же площадь в случайном месте | 71.8 | −0.15 |

Опора на номер — 0.35 − 0.33 = 0.02 п.п. при разбросе между прогонами 0.2–0.3 п.п., то есть
ноль. Абляция снята на модели v1.0 (`results/hack_ft_soup_b336_val_val_mask-*.json`). То же
видно в интерфейсе: на карте «Почему похоже» зона номера не выделяется. Карта — точное
аддитивное разложение косинуса по участкам кадра, а не Grad-CAM (`docs/ARCHITECTURE.md`).

## 7. Большие галереи

Замер поиска на векторах размерности релиза, синтезированных по статистике настоящих векторов
модели; у каждого запроса есть подсаженный правильный ответ. Галерея 10⁶ наблюдений:

| режим | мс на запрос | память индекса | верный ответ на 1-м месте |
|---|---:|---:|---:|
| точный перебор | 16.95 | 5859 МиБ | 1.000 |
| PCA-256 + HNSW | **0.45** | 977 МиБ | 0.824 |
| IVF + PQ192 | 1.34 | **183 МиБ** | **0.934** |

Для городских объёмов подходит IVF-PQ: в тридцать раз меньше памяти и в двенадцать раз быстрее
при потере 6.6% точности первого места. Таблицы для 10⁴ и 10⁵ — `results/ann_scalability.json`,
они же в интерфейсе на вкладке «О системе». В сервисе приближённый поиск включается режимом
«Быстрый» (`POST /v1/search?mode=ann`) для галерей от 256 наблюдений. Воспроизвести:
`python scripts/ann_benchmark.py --sizes 10000 100000 1000000`.

## 8. Анализ ошибок

Полный разбор — [`docs/ERROR_ANALYSIS.md`](docs/ERROR_ANALYSIS.md). Из 1213 запросов валидации:

| исход | запросов | доля |
|---|---:|---:|
| первый кандидат верный | 780 | 64.3% |
| верный ответ есть в десятке, но не первым | 146 | 12.0% |
| верного ответа нет в десятке | 44 | 3.6% |
| пары в галерее нет, запрос вне mAP | 243 | 20.0% |

Основные ошибки — одинаковые машины одной модели и цвета: без номера они различаются мелкими
деталями, которых на кадре не видно. Размер рамки ошибку почти не объясняет. Ложных принятий
10: восемь раз система ответила на запрос без пары и два раза уверенно назвала не ту машину.

```bash
# учитель ViT-L/14 на 336, первые 8 блоков заморожены

    --epochs 20 --P 5 --K 4 --freeze-blocks 8 --cam-aware --cross-cam-triplet \
    --out weights/hack_dinov2_l_336_cam
# v1.3: ученик ViT-B/14 на 392, сиды 0/2/3, на всех машинах
python -m vreid.train --config configs/hackathon.yaml --backbone dinov2_b --img-size 392 \
    --epochs 18 --P 8 --K 4 --cam-aware --cross-cam-triplet \
    --distill weights/hack_dinov2_l_336_cam/best.pt --distill-w 40 --distill-focus 4 \
    --val-frac 0 --seed 0 --out weights/all18_r392_dw40f4_s0
python scripts/model_soup.py weights/all18_r392_dw40f4_s0/best.pt \
    weights/all18_r392_dw40f4_s2/best.pt weights/all18_r392_dw40f4_s3/best.pt \
    --out weights/soup_r392dw40f4_all/best.pt
# v1.4: второй учитель — v1.3
python -m vreid.train --config configs/hackathon.yaml --backbone dinov2_b --img-size 392 \
    --epochs 18 --P 8 --K 4 --cam-aware --cross-cam-triplet \
    --distill weights/hack_dinov2_l_336_cam/best.pt,weights/soup_r392dw40f4_all/best.pt \
    --distill-w 40 --distill-focus 4 --val-frac 0 --seed 0 --out weights/all18_r392_dw40f4t2_s0
python scripts/model_soup.py weights/all18_r392_dw40f4t2_s0/best.pt \
    weights/all18_r392_dw40f4t2_s2/best.pt weights/all18_r392_dw40f4t2_s3/best.pt \
    --out weights/soup_r392dw40f4t2_all/best.pt
# двойник для замеров и выбора порога — те же команды с --no-select вместо --val-frac 0
python scripts/refusal_stress.py --run runs/hack/ft_soup_r392dw40f4t2_fit \
    --out results/refusal_stress_r392dw40f4t2.json
python scripts/choose_threshold.py --stress results/refusal_stress_r392dw40f4t2.json \
    --out results/threshold_choice_r392dw40f4t2.json              # -> 0.67
python scripts/export_release.py --weights weights/soup_r392dw40f4t2_all/best.pt \
    --val results/hack_ft_soup_r392dw40f4t2_fit_val.json --confidence top1 --threshold 0.67 \
    --threshold-choice results/threshold_choice_r392dw40f4t2.json \
    --kr --k1 3 --k2 2 --lam 0.2 --crop-pad 0.05 --out release
```

## 11. Ограничения

1. **Скорость замерена на RTX 5060 Ti**, а не на целевой RTX A5000; на другом железе и
   окружении числа будут другими.
2. **Порог выбран на галерее из 688 наблюдений.** На галерее другого размера оптимальный порог
   может сместиться; величину этого эффекта на наших данных измерить не удалось.
3. **Числа точности получены на модели-двойнике**, а не на самом релизе: релиз обучен на всех
   машинах, и отложенной части для него нет.
4. **Сервис обрабатывает одну операцию модели за раз**, до 1500 наблюдений в галерее, импорт
   синхронный, ролей пользователей нет. Векторы хранятся в СУБД, так что горизонтальное
   масштабирование возможно, но в этой версии не сделано.
5. **Данные вне репозитория.** Кадры, разметка и официальный скрипт метрики принадлежат
   владельцу данных и не публикуются. Входные CSV в `tests/` синтетические: проверяется
   форма выходных файлов, а не качество.
