# Сервис безномерной идентификации транспортного средства

Команда **«Скованные одной цепью»**: ядро и обучение — Шека Николай, сервис и интеграция — Исмаков Марат.

Система ищет один и тот же автомобиль по внешнему виду на кадрах разных камер и возвращает **отказ**, если уверенности недостаточно. OCR и распознавание госномеров не используются. Версия **v2.0** использует ансамбль **DINOv3 + CNN**, графовое ранжирование и калиброванный механизм отказа. Сервис включает веб-интерфейс, HTTP API и пакетный запуск без доступа к интернету.

| | |
|---|---|
| модель | DINOv3 ViT-L/16, 384×384 + ResNet50-IBN/GeM, 256×256 |
| финальные файлы весов | **16 файлов, 1 838 245 659 байт**, включая GPU engines и CPU-веса; лимит 2 000 000 000 байт |
| экспорт признаков | содержательный L2-нормированный CNN-вектор **512D**; внутренние сырые DINO/CNN — по 2 048D |
| хранение | PostgreSQL / SQLite, изображения и ссылки `feature_ref` на признаки DINOv3 и CNN |
| основной запуск | Linux / NVIDIA RTX A5000 SM86 / TensorRT 10.9.0.34; FP32 CPU — отдельный численный backend |
| воспроизводимость | единый manifest CLI/HTTP, SHA-256 весов и исходников, офлайн-инференс |

Презентация и видео прототипа передаются командой отдельными ссылками в конкурсной заявке. В этом репозитории находятся проект, инструкции, источники и результаты проверки.

## 1. Быстрый старт

### 1.1 Веб-сервис — одной командой

Нужны Linux, Docker Compose v2, NVIDIA Container Toolkit и совместимый драйвер NVIDIA. TensorRT engines предназначены для **SM86**; Windows/Blackwell не являются целевой средой этого комплекта.

```bash
docker compose up --build
```

Сборка устанавливает зафиксированные зависимости и скачивает недостающие веса **из v2.0**, проверяя каждый файл по SHA-256. Все веса попадают внутрь образа. Интернет нужен при сборке; во время инференса скачиваний нет.

Поднимаются PostgreSQL + pgvector, API и nginx. После готовности откройте **http://localhost:8080**. Наружу по умолчанию доступен только локальный web-порт; API и база остаются внутри Docker-сети.

| адрес | назначение |
|---|---|
| `/` | интерфейс: галерея, поиск, объяснение, экспорт |
| `/docs` | Swagger UI, локальные JS/CSS, работает офлайн |
| `/openapi.json` | схема API |
| `/health` | состояние сервиса и хранилища |
| `/v1/model` | отпечатки модели, рецепта, представления и runtime |

Для собственного окружения задайте `POSTGRES_PASSWORD`, при необходимости `VREID_API_KEY` и `WEB_PORT` через переменные среды или локальный `.env`. Секреты не включаются в репозиторий.

1. **Галерея** → импорт ZIP с `test_gallery.csv` (`image_id,x,y,w,h`) и `images/`, либо добавление отдельного изображения с рамкой автомобиля.
2. **Поиск** → изображение и рамка → найденное совпадение или отказ, top‑10, confidence, CSV/JSON.
3. **Сравнить кадры** → исходные кропы запроса и выбранного кандидата, их сходство и отдельно решение для top‑1. Доступны два отдельных режима: **«Похожие участки · эксперимент»** сопоставляет patch-признаки DINOv3; **диагностика чувствительности** закрывает области независимо. Эксперимент может ошибаться и связывать фон или разные детали; он не доказывает идентичность машины и не объясняет отказ. Расчёт соответствий выполняется на CPU по явному запросу, после него дополнительная модель выгружается; требуется минимум 3 ГиБ свободной RAM/commit. Во время расчёта другие модельные операции получают 503/Retry-After. Дополнительная GPU-память не используется.

### 1.2 Веса отдельно

```bash
python scripts/fetch_weights.py
python scripts/fetch_weights.py --verify-only
```

Используется стандартная библиотека Python; список URL, размеров и SHA — [release/weights.json](release/weights.json). Уже существующий изменённый файл не перезаписывается. Финальные веса также доступны в [GitHub Releases](https://github.com/Pelmen535/FalconTech/releases/tag/v2.0).

### 1.3 Пакетный прогон

```bash
docker build -t falcontech:2.0 .
docker run --rm --gpus all --network none --shm-size=512m \
  -v /absolute/path/to/data:/data:ro \
  -v /absolute/path/to/results:/out \
  falcontech:2.0 predict --data /data --out /out/run-001 --device cuda
```

В `/data`: `images/`, `test_query.csv`, `test_gallery.csv`. Формат рамок — XYWH. Выходная папка должна быть **новой**: существующий результат защищён от перезаписи.

| файл | содержимое |
|---|---|
| `submission.csv` | query ID и десять gallery ID, без заголовка, в исходном порядке запросов |
| `candidates.csv` | `query_id,gallery_id,confidence`; отказ — отсутствие строки для запроса |
| `embeddings.npy` | `float32 [N,512]`, сначала query в порядке CSV, затем gallery; галерейно адаптированный CNN-признак |
| `run_info.json` | параметры и отпечатки запуска |

Основная точка входа v2.0 — `scripts/october_entrypoint.py`. Для CPU используйте тот же образ без `--gpus all`, заменив `--device cuda` на `--device cpu`; численные результаты CPU и TensorRT не объявляются идентичными.

## 2. Архитектура

```text
браузер → nginx → FastAPI → OctoberAdapter → контролируемый runtime worker
                    ↓                             ↓
             PostgreSQL / SQLite          DINOv3 2048D + CNN 2048D
                    ↓                             ↓
         image_id → feature_ref       projections / gallery adaptation
                    └────────────→ ranking → confidence → отказ / кандидат
```

CLI и HTTP используют один runtime manifest, один код извлечения, ранжирования и отказа. База хранит наблюдения, изображения, рамки и явные ссылки на сырые признаки. Для ранжирования применяются содержательные проекции и статические структуры галереи. Подробный контракт HTTP — [API](docs/API.md).

Воркер имеет deadline, проверку ресурсов, корреляцию request ID и восстановление после сбоев. Добавление наблюдений, резервное копирование и восстановление учитывают raw-cache и версию представления. Старую БД v1.4 нельзя открыть как v2.0 без миграции. Команды и ограничения — [service/README.md](service/README.md).

## 3. Модель, ранжирование и отказ

DINOv3 формирует CLS + среднее patch-признаков; CNN добавляет другую геометрию сходства. После фиксированных обученных transforms используются centering/whitening по **статической gallery** и три графовых составляющих, включая вставку **одного текущего query**. Другие query и полученные по ним результаты для решения текущего запроса не используются. Это не query expansion по пакету запросов.

Влияние реранкинга зависит от данных: на локальном организаторском наборе он улучшает retrieval, на VRIC остаётся регрессия относительно fused cosine. Результаты и ограничения приведены в [отчёте A5000](docs/V2_A5000_REPORT_RU.md).

Отказ реализован замороженной цепочкой heads и правил. Дополнительная проверка противоречивого позднего принятия и её измеренный компромисс Recall/ложных ответов описаны в [отчёте от 20 октября](docs/REFUSAL_HOTFIX_20261020_RU.md). Порог публичной шкалы записан в runtime manifest; внутренние пороги, scopes и конфигурации — в закреплённых JSON. На каждом новом тестовом наборе они не подбираются. `confidence` — **калиброванная шкала принятия**, а не безусловная вероятность правильности top‑1. На сложных ракурсах возможен отказ при наличии правильного кандидата.

### Порог отказа

Финальный публичный порог **`confidence >= 0.7988346717209206`**: принятый top‑1 записывается в `candidates.csv`; при меньшем значении строки для query нет. `submission.csv` всё равно содержит десять кандидатов. Это фиксированная шкала решения, **не вероятность правильности 79,88%**.

У исходных source/night heads разные внутренние пороги: **0.47480770844997583 / 0.30021713454777316**, закреплённые в `var/three-directions-20261009/fusion-selection.json`. Их score переносится в общую шкалу через `sigmoid(logit(p) − logit(cut) + logit(public_boundary))`; значение ровно на внутреннем пороге соответствует публичной границе. Дополнительные замороженные heads могут принять ранее отклонённый запрос; их собственные пороги и scopes записаны в закреплённых `runtime-selection.json`. У финального road verifier `cut=0.6349104308612428`, `alpha=1.0`.

Выбор порогов выполнялся на исторических FIT/CAL-эпизодах с запросами без пары; исходная оценка режима отказа — `0.7·F1 + 0.3·TNR`, с ограничениями сохранности прежних решений и retrieval. Эти данные неоднократно использовались в разработке, поэтому это обоснование выбора, **не доказательство независимой калибровки на новом домене**. Происхождение весов и воспроизведение обучения — [TRAINING_PROVENANCE_V2_RU.md](docs/TRAINING_PROVENANCE_V2_RU.md).

ANN использует shortlist и консервативное дополнение для сохранения точного top‑10. Он может развернуться в полный поиск и на проверенных галереях не имеет подтверждённого преимущества в скорости. Миллионная галерея для текущего backend не квалифицирована. Пустая/слишком малая после исключений галерея и неподдерживаемые sparse multibox-сценарии отклоняются явно.

## 4. Проверка на A5000 и сравнение с v1.4

Подробности, фактическая среда, полный охват и незакрытые ограничения — [отчёт A5000](docs/V2_A5000_REPORT_RU.md). Ниже результаты заново выполненных Linux-прогонов 20 октября 2026 года, посчитанные неизменённым scorer организаторов. Все значения — проценты.

| Набор и версия | mAP@10 | Rank‑1 | Rank‑5 | Precision | Recall scorer | F1 | TNR |
|---|---:|---:|---:|---:|---:|---:|---:|
| external — v1.4 release | 42.9760 | 56.0000 | 69.9000 | 60.0243 | 68.0441 | 63.7831 | 45.0000 |
| external — v2.0 | **76.1620** | **80.0000** | **91.9000** | **88.4211** | **72.2581** | **79.5266** | **82.0000** |
| organizer local — v1.4 release | 99.5472 | 99.4845 | 99.8969 | 100.0000 | 97.6289 | 98.8002 | 100.0000 |
| organizer local — v1.4 FIT-only контроль | 82.8459 | 80.8247 | 91.4433 | 98.9201 | 94.6281 | 96.7265 | 96.7078 |
| organizer local — v2.0 | 87.0658 | 83.9175 | 94.6392 | 98.6444 | 97.8283 | 98.2347 | 95.8848 |
| VRIC661 — v2.0 | 48.1207 | 42.6263 | 53.9394 | 67.2043 | 27.2331 | 38.7597 | 84.9398 |

**Это результаты разработки, не независимый holdout.** Литеральная релизная v1.4 обучалась на всех организаторских TRAIN ID, включая ID локального organizer-сравнения: её 99.55% не является честным holdout-эталоном. Сравнение с существовавшим v1.4 FIT-only контролем вынесено в отчёт отдельно. Некоторые исторические external/transfer-контексты позднее использовались в обучении головы отказа; их также нельзя считать независимыми. Метрики закрытого стенда и итоговые баллы определяют организаторы.

`Recall scorer = TP/(TP+FN)`, `TP/Nknown` — отдельная доля правильных принятий. Ошибочно принятый известный запрос учитывается в FP; поэтому один Recall не описывает все ошибки. Для v2.0: external TP/Nknown **67.20%**, organizer local **97.5258%**, VRIC661 **25.2525%**.

### 4.1 Производительность

Одинаковые 64 JPEG/рамки, A5000, ограничения 8 CPU / 16 ГиБ RAM, 4 preprocessing workers, 50 прогревов, 300 B1-замеров с CUDA sync и по 30 секунд на B1/8/16/32. Два завершённых процесса на каждую версию; значения ниже — диапазон между ними, без обещания статистически значимого преимущества.

| Версия | B1 median, мс | лучший batch FPS в двух прогонах | выборочный максимум GPU, МиБ |
|---|---:|---:|---:|
| v1.4 release | **29.07–29.23** | 131.44–139.34 | 1625 |
| DINOv3 + CNN до оптимизации | 36.74–36.95 | 128.54–128.67 | 3745 |
| v2.0 | 35.41–35.74 | 132.50–134.58 | **1497** |

Замер включает чтение JPEG, декодирование, crop, preprocessing, энкодеры и преобразования признаков; поиск, отказ и HTTP в него не включены. GPU-память измерена `nvidia-smi` каждые 250 мс на выделенном GPU — это выборочный максимум процесса/устройства, не точный allocator peak и не гарантия максимума на любой галерее. v2.0 быстрее прежней October A в этих замерах и использует меньше GPU-памяти, но не превосходит v1.4 по B1 latency. Замеры, выполненные по другим протоколам, в эту таблицу не включены.

Текущая проверочная среда — driver 570.211.01 / CUDA 12.8 runtime. Точное соответствие упомянутому организаторами CUDA 12.2 не проверено; одинаковая A5000 не делает драйверы одинаковыми.
