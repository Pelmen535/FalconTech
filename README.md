# Сервис безномерной идентификации транспортного средства

Команда **«Связанные одной цепью»**. Кейс «Фалькон Тех», хакатон 2026.
Ядро и обучение — Шека Николай, сервис и интеграция — Исмаков Марат.

Система находит один и тот же автомобиль на кадрах с разных камер **без использования
государственного номера** и умеет **отказаться отвечать**, когда подходящего автомобиля в
базе нет. Номер в данных уже анонимизирован, и мы отдельно показываем — числом и картинкой, —
что решение на него не опирается.

В репозитории два независимых способа запуска одной командой: **прототип** (веб-интерфейс,
API, база) и **конкурсный прогон** (`/data` → три файла сдачи). Оба используют одно ядро,
одни веса и один замороженный рецепт.

## 1. Запуск одной командой

### 1.1 Прототип: интерфейс, API и база

```bash
cp .env.example .env          # при необходимости поправьте порт и устройство
docker compose up --build
```

Открыть **http://localhost:8080**. Там же:

| адрес | что это |
|---|---|
| `/` | веб-интерфейс: загрузка кадра, рамка мышью, топ-10, отказ, объяснение, выгрузка |
| `/docs` | Swagger UI — интерактивная спецификация OpenAPI, работает без интернета |
| `/openapi.json` | машинное описание API |
| `/health` | состояние процесса, хранилище, отпечатки модели и рецепта |

Проверить работоспособность за два клика: вкладка **Галерея** → «Загрузить демо-галерею»
(20 настоящих кадров организаторов), вкладка **Поиск** → «Взять демонстрационный кадр» →
«Найти автомобиль». Никаких внешних файлов для этого не нужно.

Поднимаются три контейнера: `db` (PostgreSQL + pgvector), `api` (инференс и HTTP),
`web` (nginx, тонкий клиент). Наружу публикуется только `web`.

### Что посмотреть за три минуты

1. **Поиск и отказ.** «Галерея» → «Загрузить демо-галерею» → «Поиск» → «Взять
   демонстрационный кадр» → «Найти автомобиль». Видно топ-10, косинусы, решение о принятии
   и порог, по которому оно принято.
2. **Почему похоже.** Кнопка под любым кандидатом. Две карты вклада — на запросе и на
   кандидате. Зона номера на них не подсвечена: это то же утверждение, что и абляция
   из раздела 6, но его видно глазами.
3. **Отказ вживую.** Загрузите свой кадр с автомобилем, которого в галерее нет: система
   ответит «Отказ от сопоставления» и покажет, какой кандидат не дотянул до порога.
4. **Спецификация.** Ссылка «OpenAPI · Swagger» в шапке: тот же API, который использует
   страница, целиком, с возможностью выполнить запрос прямо из браузера.
5. **Масштабируемость.** Одноимённая вкладка: измеренные цифры поиска на галереях до 10⁶.
6. **Конкурсный прогон.** `docker compose run --rm predict` — те же веса, тот же рецепт,
   три файла сдачи.

### 1.2 Конкурсный прогон: три файла сдачи

```bash
docker build -t vreid:1.0 .
docker run --rm --gpus all --shm-size=2g \
  -v /путь/к/данным:/data:ro -v /путь/куда/писать:/out vreid:1.0
```

или тем же compose:

```bash
docker compose run --rm predict
```

Читает `/data/images`, `/data/test_query.csv`, `/data/test_gallery.csv`. Пишет в `/out`:

| файл | содержимое |
|---|---|
| `embeddings.npy` | `float32 [N, 1536]`: сначала все query в порядке `test_query.csv`, затем вся gallery в порядке `test_gallery.csv` |
| `submission.csv` | `query_id, gallery_id_1 … gallery_id_10` — **без строки заголовка**, ровно десять кандидатов на каждый запрос, всегда |
| `candidates.csv` | заголовок `query_id,gallery_id,confidence`; **отказ — это полное отсутствие строк** для данного `query_id` |
| `run_info.json` | время, число отказов, отпечатки модели, рецепта и входных CSV (не является артефактом сдачи) |

Рантайм полностью офлайн: `HF_HUB_OFFLINE=1`, веса внутри образа, проверено прогоном
с `--network none`. `--shm-size=2g` нужен потому, что загрузчик передаёт батчи через
`/dev/shm`; без флага прогон не падает, а сам снижает число воркеров.

### 1.3 Если что-то не собирается

* **Карта новее CUDA 12.1** (RTX 40xx/50xx). Релизная база собрана под стенд жюри
  (RTX A5000, драйвер CUDA 12.2) и на Blackwell не запустится. Локальная сборка:
  раскомментируйте три строки в конце `.env.example`, либо
  ```bash
  docker build --build-arg BASE_IMAGE=pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime \
               --build-arg PIP_FLAGS=--break-system-packages \
               --build-arg REQUIREMENTS=requirements-infer-dev.txt -t vreid-dev .
  ```
* **Нет GPU.** Основной compose резервирует видеокарту, и на машине без NVIDIA-рантайма
  запуск упал бы ещё до старта контейнера. Для такой машины есть готовый файл:
  ```bash
  docker compose -f docker-compose.yml -f docker-compose.cpu.yml up --build
  ```
  Модель та же и ответы те же, отличается только скорость: проверено — импорт двадцати
  кадров и поиск занимают около 12 секунд вместо долей секунды. Для конкурсного прогона
  на CPU достаточно запустить `docker run` без `--gpus all`.
* **Путь с кириллицей.** buildkit отказывается собирать через `bake`, если путь к проекту
  не ASCII. Помогает `COMPOSE_DOCKER_CLI_BUILD=0 docker compose build` или распаковка в
  каталог с латинским именем.

## 2. Архитектура

Подробно — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Коротко:

```
браузер ──▶ web (nginx: страница и единственный публикуемый порт)
                 │ /v1, /health, /docs, /openapi.json
                 ▼
            api (FastAPI + ядро vreid + веса релиза)
                 │ SQL                      │ файлы модели
                 ▼                          ▼
            db (PostgreSQL + pgvector)   release/model.pt + recipe.json

то же ядро и те же веса, отдельным запуском:
  /data ──▶ predict (batch, офлайн) ──▶ embeddings.npy, submission.csv, candidates.csv
```

Почему конкурсный прогон не сделан вызовом сервиса: у него другой контракт корректности.
Жюри запускает его одной командой в изолированном окружении, и никакая часть продукта не
должна иметь возможности повлиять на результат. Общее у них ровно то, что и должно быть
общим, — ядро `vreid/` и `release/`.

Совпадение HTTP-ответа с конкурсным CLI не декларируется, а проверяется тестом
`tests/service/test_core.py` на реальной сдаче: те же топ-10, те же решения об отказе,
тот же косинус до пятого знака.

## 3. Модель и алгоритмы

**Backbone.** DINOv2 ViT-B/14, вход 336×336, эмбеддинг `concat(CLS, mean(patch tokens))`
через BNNeck → **1536 float32**, L2-нормирован. Веса fp16, **164 МиБ**. Вторая модель —
ViT-L/14 336 — работает только ре-ранкером второй ступени (ниже); в лимит 2 ГБ входят обе.

**Обучение.** ArcFace + батч-хард триплет, BNNeck, PK-сэмплер с кросс-камерными позитивами,
дистилляция геометрии сходств от DINOv2-L/14 336 (Tung & Mori: переносятся не сами векторы,
а матрица попарных косинусов внутри батча — размерности учителя и ученика могут не совпадать).
18 эпох, обучение на всех 1541 личностях, без отбора эпохи по валидации.

**Релиз — усреднение весов (model soup)** трёх прогонов одного рецепта с разными сидами.
Прироста качества суп не даёт: 70.66 против среднего участников 70.54. Но **разброс между
сидами одного рецепта — 2.9 пункта** (71.63 / 71.24 / 68.73), и выбирать «лучший одиночный»
по валидации на таком шуме — лотерея. Суп даёт то же матожидание при меньшей дисперсии и
не стоит ни миллисекунды на инференсе.

**Инференс.** Кроп по рамке с паддингом 5%, ускоренный декод JPEG в уменьшенном масштабе
(когда рамка это позволяет — снимает ввод-вывод с ~42 до 21 мс на ТС), forward,
L2-нормализация. Ранжирование — косинус, затем **k-reciprocal 6/2** внутри одного запроса и
галереи с параметрами `k1=3, k2=2, λ=0.2`. Ре-ранжирование не входит в замер латентности
жюри, то есть достаётся бесплатно — и именно поэтому его параметры стоит искать как
следует, а не брать первое работающее значение.

**Как выбраны 3/2/0.2.** Прежние 6/2/0.3 были первой строкой грубой сетки 6/10/15/20,
то есть краем диапазона. Полная сетка из 93 точек дала оптимум внутри: 3/2/0.2. Выбор
сделан на кеше двойника релиза и независимо подтверждён на кеше второй модели — лучшая
точка совпала, ранговая корреляция двух поверхностей 0.957. Прирост mAP@10 +0.57 п.п.
на двойнике и +1.09 п.п. на второй модели, rank-1 +1.13 и +1.03. Режим отказа не
меняется вовсе: ре-ранжирование не сдвигает топ-1 ни у одного из 1213 запросов, поэтому
уверенность и набор принятых запросов те же. Воспроизвести: `python scripts/rerank_grid.py`.
Оговорка: оба кеша имеют галерею 688, а закрытый тест 750, и перенос оптимума `k1` на
другой размер галереи мы не измеряли.

**Каскад: лёгкая модель ищет, тяжёлая проверяет.** После k-reciprocal порядок внутри
топ-30 уточняет второй бэкбон — DINOv2 ViT-L/14 336, тот самый, что был учителем при
дистилляции. Итоговая оценка кандидата — `0.9·(косинус ViT-L) + 0.1·(оценка первой
ступени)`, обе величины приводятся к [0,1] минимаксом внутри строки запроса. На отложенной
валидации это mAP@10 **74.21 → 78.97** и rank-1 70.72 → 76.29.

Число честное в строгом смысле. Первый замер (78.51) был снят с ре-ранкером, у которого
лучшая эпоха выбиралась по той же валидации, — то есть мог быть завышен на неизвестную
величину. Мы обучили двойника с `--no-select`, который эту валидацию при выборе эпохи не
видел: он дал **78.97**, то есть подозрение снялось, и в сторону улучшения.
`results/cascade_verify_honest.json`.

Почему это не обход правил, а предусмотренный ими сценарий:

* «Поиск по gallery и rerank **не входят**» в `latency_b1` (ответы 31, 32);
* лимит 2 ГБ считается по сумме весов «основного backbone, auxiliary-моделей,
  классификаторов, ensemble и **reranker**» (ответы 34, 37) — отдельная модель-ре-ранкер
  названа прямо, и её вес мы в лимит закладываем: 172 + 608 = 780 МБ из 2000;
* «`submission.csv` может быть результатом per-query каскада: cosine shortlist,
  pairwise/local-feature проверка или per-query k-reciprocal» (ответ 28);
* `embeddings.npy` у организаторов идёт в справочный раздел, балл считается по
  `submission.csv` — расхождение порядка с косинусом по `embeddings.npy` штатно. Мы кладём
  в него векторы **основной** модели: именно она стоит в замеряемом пути.

**Чего мы не прячем.** Замеряемая жюри латентность от каскада не меняется, а настоящая
цена запроса — меняется: к 33.2 мс добавляется форвард ре-ранкера. `vreid/bench_full.py`
меряет обе и пишет в `results/bench_full.json` три поля: `cascade_reranker_ms`,
`latency_ms_end_to_end` и `latency_score_if_reranker_counted` — балл, который латентность
получила бы, если бы ре-ранкер считали. Мы считаем правила ясными, но выбор шкалы за жюри,
и обе цифры должны быть у него перед глазами, а не одна.

**Режим отказа каскад не трогает.** Уверенность остаётся сырым косинусом **основной**
модели к тому кандидату, который реально уходит в файл. Порог 0.55 перекалибровывать не
нужно: при том же замороженном пороге балл блока 96.40 → 96.55. Проверено на обоих кешах.

**Независимость запросов** (ответ 38) обеспечена по построению, а не проверкой на выходе:
столбцы запросов исключены из соседства в k-reciprocal, матрицы считаются фиксированной
формы, сортировки стабильные, память ограничивает размер пачки, а не выбор алгоритма.
Проверки: `scripts/check_query_independence.py` (топ-10 совпал у 666 из 666 при удалении и
перестановке остальных запросов), `scripts/check_tie_independence.py` (расхождение 0.000e+00
на точных ничьих и при любом размере пачки).

### Что отвергнуто и почему

| вариант | что даёт | почему не в релизе |
|---|---|---|
| DINOv2-L **основной моделью** | mAP 78.1 / 81.2, +6 пунктов | форвард примерно втрое тяжелее: латентность уходит к 57 мс, пропускная ниже 50 FPS — около −14 баллов производительности против +2.9 за точность. Взят ре-ранкером второй ступени, где по правилам не оплачивается (см. выше) |
| дистилляция от трёх учителей сразу | цель усредняется по матрицам сходств трёх ViT-L; на инференсе бесплатно | измерено и отвергнуто: 69.42 против 71.63 у того же рецепта с одним учителем. Разброс между сидами одного рецепта 2.90, так что это внутри шума, — но прироста нет, а на одном шуме релиз не меняют. `results/training_multiteacher.json` |
| выборочная тяжёлая проверка (только неуверенные запросы) | сняла бы риск каскада: медиана латентности не выросла бы | измерено и отвергнуто: при проверке 46% самых неуверенных запросов прирост 74.21 → 74.94, шестая часть от полного. | ре-ранкер попроще (ViT-B 448 или вторая ViT-B) | был бы втрое дешевле ViT-L | измерено: +0.05 и +0.7 п.п. Выигрыш даёт именно качество ViT-L, а не разнообразие моделей |
| локальное сопоставление патчей | ответ 28 его разрешает | измерено и отвергнуто: само по себе ранжирует на mAP 15–19 против 74.2 у базы, а слияние лучше всего при весе 0 — на обоих кешах и при любом пороге сходства патчей. `results/local_verify.json` |
| отбеливание и центрирование эмбеддинга | бесплатно на инференсе | центрирование по галерее даёт +0.31 п.п. без ре-ранжирования, но с ним разнонаправленно на двух кешах; PCA-отбеливание хуже базы при любой степени. Это шум, рецепт не меняется |
| ансамбль двух моделей | — | удваивает время сети; при линейной шкале окупается только приростом около +5.3 п.п. mAP |
| TTA (горизонтальный флип) | обычно +0.3…1.0 п.п. | удваивает форвард; −5 баллов производительности против +0.2 за точность |
| DBA + query expansion | mAP 75.0 вместо 74.3 | **запрещено правилами** (ответ 38) |
| детектор зоны номера в бою | — | 50 мс на кроп при бюджете 8 мс, и, как показала абляция, не нужен |

Разрыв между учителем и студентом означает, что усиление дистилляции — самый дешёвый
оставшийся рычаг по mAP из тех, что ничего не стоят на инференсе. Дистилляция теперь
принимает нескольких учителей через запятую: цель усредняется по их матрицам сходств.

## 4. Метрики

Все числа сняты по правилу жюри: из галереи удаляются только объекты, у которых совпали
**и** `vehicle_id`, **и** `camera_id` с запросом; `AP@10` нормируется на `min(n_pos, 10)`;
запрос без валидных положительных исключается из mAP, но участвует в оценке отказа.

**Числа посчитаны эталонным скриптом организаторов.** `organizer/evaluate.py` получен
21.09 вместе с `example_submission.zip`; меток закрытого теста у нас по-прежнему нет,
зато они есть на нашей валидации — поэтому мы собрали из неё набор ровно того формата,
который ждёт эталон, и прогнали его. Наша собственная реализация метрики совпала с
эталонной до 1e-16 по всем полям. Воспроизвести:
`python scripts/score_validation_with_official.py`.

Измерено на отложенной валидации: 1213 запросов, галерея 688, из них 243 запроса (20.0%)
без пары. Модель — «честный двойник» релиза: тот же рецепт, те же три сида, те же 18 эпох,
но обучен на fit-сплите, так что 307 валидационных личностей он не видел. Сам релиз измерить
нельзя — он обучен на всех личностях.

| что | значение | источник |
|---|---:|---|
| mAP@10 без постобработки | **70.5** | `results/hack_ft_soup_b336_fit_val.json` |
| **mAP@10 с k-reciprocal 3/2/0.2 (в релизе)** | **74.21** | эталонный scorer, `results/official_validation/` |
| rank-1 | 70.72 | там же |
| rank-5 | 86.60 | там же |
| mAP по полному ранжированию (справочно) | 71.46 | там же |
| mINP (справочно, в балл не входит) | 65.74 | там же |
| **отказ: 0.7·F1 + 0.3·TNR при пороге 0.55** | **96.4** (F1 96.8, TNR 95.5) | там же |
| — то же без одно-камерных дубликатов (стресс) | 63.2 | там же |
| отказ, замороженный порог на отложенной половине машин | 97.2 | `results/refusal_audit_fit.json` |

### Производительность

Замерено методикой организаторов: медиана 300 прогонов после 50 прогревочных, CUDA sync
до и после каждого; пропускная — устойчивый прогон не короче 10 с на батчах 1/8/16/32,
в зачёт лучший FPS. В латентность входят чтение, декодирование, кроп, препроцессинг,
forward и нормализация; поиск и ре-ранжирование не входят.

| что | значение | балл по шкале организаторов |
|---|---:|---|
| латентность batch=1, медиана | **31.7 мс** | 10/10 (полный балл до 40 мс) |
| лучший FPS (batch 8) | **188.9** | 10/10 (полный балл от 100 FPS) |
| из них чтение+декод+кроп+препроцессинг | 23.2 мс | — |
| суммарный размер весов | 164 МиБ из 2048 | — |

## 5. Порог отказа и его обоснование

Порог **0.55** заморожен в `release/recipe.json` вместе с обоснованием (поле
`threshold_choice`) и не подбирается во время работы. Уверенность — **сырой косинус**
выбранного кандидата, не вероятность. Организатор не применяет к ней свой порог: само
наличие строки в `candidates.csv` уже является решением команды.

Порог выбран **ниже оптимума валидации** сознательно. В нашей валидации и в открытом тесте
галерея собрана по одному кадру на трек «машина × камера», поэтому у **всех** запросов с
парой в галерее лежит кадр той же машины с той же камеры — почти дубликат, медиана косинуса
0.912. Закрытый тест гарантирует только кросс-камерную пару (ответ 17). Без дубликатов
медиана падает до 0.517, и высокий порог начинает отказывать тем, кому надо отвечать:

| порог | галерея с дубликатами | галерея без дубликатов |
|---:|---:|---:|
| 0.60 (оптимум валидации) | 96.7 | 54.4 |
| **0.55 (в релизе)** | **96.4** | **63.2** |
| 0.48 (минимакс, максимизирует худший случай) | 92.6 | 69.7 |

Точка безразличия — уверенность 0.913 в том, что дубликаты будут. Страховка стоит 0.08 балла
общей сотни, а выплата 0.89. Воспроизвести: `python scripts/refusal_stress.py`.

На открытом тесте этот порог даёт **69 отказов из 1110 (6.2%)**.

## 6. Номерной знак

Номера в данных организаторов уже анонимизированы пикселизацией. Замер на кропе показал,
что связные области постоянной яркости там — идеальные прямоугольники 72×15 px, выстроенные
решёткой; на номер шириной 320 px приходится 4–5 ячеек, то есть от символов не остаётся
ничего.

Но «символов не видно» ещё не значит «модель не опирается на эту зону»: остаются положение,
размер и средний цвет пятна. Поэтому проведена абляция **с контролем равной площади**: зона
номера ищется детектором (`vreid/plate.py`, находит на 94.0% из 11 416 кропов) и закрывается
сплошной заливкой; контроль — такой же по площади прямоугольник там, где номера заведомо нет.

| вариант | mAP@10 | Δ |
|---|---:|---:|
| без маски | 72.0 | — |
| зона номера закрыта | 71.6 | −0.35 |
| контроль: та же площадь выше по кузову | 71.6 | −0.33 |
| контроль: та же площадь в случайном месте | 71.8 | −0.15 |

Опора на номер = 0.35 − 0.33 = **0.02 п.п.** при разбросе между прогонами 0.2–0.3 п.п.,
то есть ноль: закрыть номер стоит ровно столько же, сколько закрыть такой же кусок бампера.

Первая версия проверки была фиксированным прямоугольником «низ по центру» и давала −7.4 п.п.,
но он закрывал 17% кропа, а настоящая зона номера — около 1%. Те −7.4 были про размер маски,
а не про номер.

То же самое видно глазами: в интерфейсе у любого кандидата есть кнопка «Почему похоже», и
зона номера на карте вклада не подсвечена. Это не Grad-CAM, а точное аддитивное разложение
косинуса по участкам кадра — см. `docs/ARCHITECTURE.md`, раздел 5.

## 7. Масштабируемость

Поиск по галерее не входит в замер производительности жюри. Раздел отвечает на другой
вопрос: что будет, когда галерея вырастет с 750 наблюдений до городского миллиона.

Измерено на векторах размерности релиза, синтезированных по ковариации настоящих
эмбеддингов (у белого шума нет структуры, на которой работает PCA, и любой ANN на нём
выглядел бы плохо по причине, не имеющей отношения к делу). У каждого запроса есть
подсаженный правильный ответ, поэтому меряется не только совпадение списков.

Галерея 10⁶ наблюдений, размерность 1536:

| режим | мс на запрос | память индекса | байт на вектор | верный ответ на 1-м месте |
|---|---:|---:|---:|---:|
| точный перебор | 16.95 | 5859 МиБ | 6144 | 1.000 |
| PCA-256 + HNSW | **0.45** | 977 МиБ | 1024 | 0.824 |
| IVF + PQ192 | 1.34 | **183 МиБ** | 192 | **0.934** |

Вывод, который мы защищаем: для городских объёмов берётся IVF-PQ — он даёт тридцатикратную
экономию памяти и двенадцатикратное ускорение, теряя 6.6% точности первого места; PCA+HNSW
быстрее, но теряет больше. Полные таблицы для 10⁴ и 10⁵ — `results/ann_scalability.json`,
они же показаны на вкладке «Масштабируемость» в интерфейсе.

Тот же индекс встроен в боевой путь: `POST /v1/search?mode=ann`. На галерее меньше 256
записей ANN не включается — обход графа дороже полного перебора, и сервис пишет об этом
в ответе, а не делает вид, что применил.

Воспроизвести: `python scripts/ann_benchmark.py --sizes 10000 100000 1000000`.

## 8. Анализ ошибок

Полный разбор с картинками — [`docs/ERROR_ANALYSIS.md`](docs/ERROR_ANALYSIS.md). Коротко,
из 1213 запросов валидации:

| исход | запросов | доля |
|---|---:|---:|
| первый кандидат верный | 686 | 56.6% |
| верный ответ есть, но не первый — оператор исправит глазами | 209 | 17.2% |
| верного ответа нет во всей десятке — настоящий промах | 75 | 6.2% |
| валидной пары нет, запрос вне mAP | 243 | 20.0% |

Характер ошибок: белые фургоны и тёмные кроссоверы одной модели. Это не деградация
признака, а исчерпание визуальной информации — без номера такие машины различаются
мелкими деталями, которые на кадре 336×336 после пикселизации не видны. Размер рамки в
наших данных ошибку не объясняет: размах rank-1 между квартилями площади около 13 п.п.
и не монотонен.

Ложные принятия делятся надвое: 11 раз система ответила на запрос без пары и 4 раза
уверенно назвала не ту машину. Вторая половина опаснее — отказ тут не помог бы.

### 9.4 Воспроизводимость сдачи

Все сравнения — `scripts/compare_outputs.py`, логи всех шагов — `logs/`, имя файла равно
имени шага очереди (`journal/run_queue16.ps1`).

| что сравнивалось | результат |
|---|---|
| два одинаковых запуска контейнера | совпали **бит в бит** (0 из 11 100 ячеек) |
| контейнер без `--shm-size` | совпал бит в бит |
| контейнер с `--network none` | совпал бит в бит — рантайм действительно офлайн |
| прогон до и после интеграции сервиса | совпал бит в бит |
| нативный прогон против контейнерного | **расходится**: 35 ячеек ранжирования из 11 100 (0.3%), эмбеддинги до 4.5e-04 |
| код до и после чистки читаемости (133 правки в двух файлах) | совпало всё, кроме трёх описаний `--help`, которые правились намеренно |

Две последние строки называем вслух. Разные версии Pillow и NumPy дают разный порядок
суммирования и чуть иной декод, а fp32 на CPU отличается от fp16-autocast на GPU; на точных

одного образа результат детерминирован бит в бит при любом числе воркеров, любом размере
пачки и с сетью или без. Прогон релизного образа на CPU (669 с) сделан как проверка, что
образ, который соберёт жюри, действительно отрабатывает от начала до конца и пишет
корректные файлы: форма всех трёх артефактов в порядке, отказов ровно столько же.

   отвлекающие» измеряет диапазон 683→688 и даёт 0.01 п.п. Экстраполировать это на 750 нельзя,

4. **Числа получены на двойнике релиза**, а не на самом релизе: сам релиз обучен на всех

   `release/recipe.json`, поле `source`.
5. **Сервис — одна операция модели одновременно**, до 1500 наблюдений в галерее, импорт
   синхронный, ролей пользователей нет. Схема допускает горизонтальное масштабирование

6. **Веса в git.** `release/model.pt` — 164 МиБ, это больше лимита GitHub на файл без
   Git LFS. В репозитории настроен `.gitattributes` для LFS; если LFS недоступен, забирайте
   `model.pt` из архива поставки — его SHA-256 записан в `reports/MANIFEST.json`.
